## 职责

对代码进行质量审查，识别问题、提出改进建议，并在用户授权后修复问题、输出审查报告。

## 评分维度

> 评分维度映射到三视角审查：正确性/安全性/性能/规范 → 专家视角；设计模式/惯用写法 → 架构视角；可读性/可维护性 → 找茬视角

| 维度 | 权重 | 检查内容 | 对应视角 |
|------|------|----------|----------|
| **正确性** | 20% | 逻辑、边界、异常处理 | 🧬专家 |
| **安全性** | 15% | 注入、泄露、敏感信息 | 🧬专家 |
| **可读性** | 15% | 命名、注释、结构 | 😈找茬 |
| **可维护性** | 10% | 重复、圈复杂度、耦合 | 😈找茬 |
| **性能** | 10% | 资源、算法复杂度、数据结构、分配压力 | 🧬专家 |
| **规范** | 10% | 语言惯例、风格统一 | 🧬专家 |
| **设计模式** | 10% | 模式选型 | 🏗️架构 |
| **惯用写法** | 10% | 语言惯用法 | 🏗️架构 |

## 审查流程

### Phase 0: 接收

1. 接收代码片段或文件路径
2. 识别语言
3. 确定审查范围

### Phase 1: 静态分析

1. 语法检查
2. 圈复杂度计算
3. 重复代码检测
4. 安全扫描

### Phase 2: 多视角审查

**🧬 专家视角**
- 正确性：边界条件
- 安全性：潜在风险
- 性能：算法效率

**🏗️ 架构视角**
- 设计模式：是否有更合适的模式
- 算法效率：时间/空间复杂度是否最优
- 数据结构：选型是否匹配访问模式
- 分配压力：热路径是否有不必要的 GC 分配
- 惯用写法：是否用了语言的最佳实践

**😈 找茬视角**
- 可读性：命名清晰度
- 容错性：异常处理
- 可维护性：模块化程度

### Phase 3: 输出报告

根据下方"输出报告格式"章节生成完整审查报告，包含：
1. 基本信息（语言、行数、复杂度）
2. 问题列表（按严重性分级）
3. 全部 8 个维度的评分
4. 总结与建议

### Phase 4: 编译验证

审查通过后，检查代码是否能正确编译/运行语法检查。
1. 根据语言选择编译/检查命令（见编译-修改循环章节的语言编译命令表）
2. 执行编译/检查
3. 通过 → 输出最终报告
4. 失败 → 进入编译-修改循环

## 🤖 子 Agent 审查机制

> **必须启用子 Agent 进行多视角审查**，禁止在主 Agent 内自行完成审查。

### 派发规则

| 子 Agent | 角色 | 职责 | 模型 |
|----------|------|------|------|
| 🔬 专家 Agent | `explorer` | 审查正确性、安全性、性能、规范 | 继承默认 |
| 🏗️ 架构 Agent | `explorer` | 审查设计模式、算法效率、数据结构、分配压力、惯用写法 | 继承默认 |
| 😈 找茬 Agent | `explorer` | 审查可读性、可维护性、容错性、文档，用保守 vs 激进对抗分析 | 继承默认 |

### 角色 Prompt

#### 专家 Agent Prompt 模板

```
你是一位代码质量专家，负责审查以下代码。

审查对象：{file_path}
审查内容：{code_content}
语言：{language}

请从以下四个维度逐一评估：
1. 正确性 — 逻辑正确、无 bug、边界条件处理

3. 性能 — 算法效率、资源使用
4. 规范 — 符合语言最佳实践

每个维度给出：
- 判定（通过/不通过）
- 具体问题列表（如有，标注文件:行号）
- 改进建议（如有）


返回格式：
| 位置 | 问题 | 严重性 | 建议 |
```

## 审查-修改循环

### 流程

```
┌─────────────────────────────────────────────────┐
│                  主 Agent                        │
│  1. 完成代码生成/修改                             │
│  2. 并行派发专家 Agent + 架构 Agent + 找茬 Agent  │
│  3. 等待三者返回                                  │
│  4. 汇总问题 → 执行修改                          │
│  5. 判断终止条件                                  │
│     ├─ 未满足 → 回到步骤 2（新一轮审查）          │
│     └─ 满足 → 进入编译验证                       │
└─────────────────────────────────────────────────┘
```

### 规则

1. **审查环节**：必须并行派发三个子 Agent 执行审查，当前 Agent 不得自行审查
2. **修改环节**：由当前 Agent 自己执行修复
3. **每轮审查范围**：已修改文件 + 受影响的相邻文件
4. **新引入检查**：修复不能引入新问题（编译错误、逻辑回归）
5. **终止条件**：连续两轮审查三方均无新问题才结束
6. **子 Agent 异常处理**：任一子 Agent 超时或返回异常时，跳过该视角，用剩余视角的结果继续；三个全部失败则主 Agent 自行审查兜底

### 终止条件

**连续两轮审查**（专家 + 架构 + 找茬均判定「不需要修改」）→ 停止循环。

| 轮次 | 专家判定 | 架构判定 | 找茬判定 | 主 Agent 行为 |
|------|---------|---------|---------|--------------|
| 第 N 轮 | 需要修改 | 任意 | 任意 | 汇总修改，继续 |
| 第 N 轮 | 不需要 | 需要修改 | 任意 | 汇总修改，继续 |
| 第 N 轮 | 不需要 | 不需要 | 需要修改 | 汇总修改，继续 |
| 第 N 轮 | 不需要 | 不需要 | 不需要 | 计数 +1，继续下一轮 |
| 第 N+1 轮 | 不需要 | 不需要 | 不需要 | **连续两轮通过 → 停止** |
| 第 N+1 轮 | 任意一方需要修改 | — | — | 计数重置为 0，继续 |

### 安全阀

- **最大轮次：5 轮**。达到 5 轮仍未连续两轮通过，停止循环，在报告中标注「已达到最大审查轮次，以下为遗留问题」。
- 每轮审查后，主 Agent 必须输出本轮汇总：发现了几个问题、修改了什么、下一轮是否继续。

### 每轮输出

```markdown
### Round N: 审查结果

| 视角 | 发现 | 修复 | 新引入 |
|------|------|------|--------|
| 🔬 专家 | X | Y | Z |
| 🏗️ 架构 | X | Y | Z |
| 😈 找茬 | X | Y | Z |

修复清单：
1. `文件:行号` — 问题描述 → 修复方式
2. ...
```

### 最终输出

```markdown
## 审查-修改循环完成

| 轮次 | 专家 | 架构 | 找茬 | 修复 | 新引入 |
|------|------|------|------|------|--------|
| Round 1 | 5 | 3 | 4 | 12 | 2 |
| Round 2 | 2 | 0 | 0 | 2 | 0 |
| Round 3 | 0 | 0 | 0 | 0 | 0 |

总计：X 个问题，Y 轮修复，循环终止原因：连续两轮三方审查均无问题
```

### 注意事项

- 修复时只改必须改的代码，不做额外重构
- 每轮修复后必须通过子 Agent 重新审查已修改文件
- 如果修复引入了编译错误，立即在当前轮次修复
- 保留每轮的修复记录，便于回溯

## 编译-修改循环

审查-修改循环通过后，进入编译-修改循环，确保代码能正确编译。

### 流程

```
审查-修改循环 → 通过
      ↓
编译-修改循环 → 通过 → 结束
      ↓
   编译失败 → 修复 → 再编译 → 直到通过
```

### 规则

1. **编译命令**：根据语言选择对应的编译/检查命令
2. **修复范围**：只修复编译错误，不做逻辑改动
3. **终止条件**：连续两轮编译均无新错误才结束，最大轮次 10 轮
4. **最大轮次：10 轮**。达到 10 轮仍未通过，停止循环，在报告中标注「已达到最大编译轮次，以下为遗留编译错误」。

### 语言编译命令

| 语言 | 编译/检查命令 |
|------|--------------|
| C# (Unity) | 检查 asmdef 引用 + namespace + using |
| TypeScript | `npx tsc --noEmit` |
| Go | `go build ./...` |
| Rust | `cargo check` |
| Python | `python -m py_compile` 或 `mypy .` |
| JavaScript | `node --check <file>` |

### 每轮输出

```markdown
### Compile Round N: 编译结果

| 错误数 | 修复 | 文件 |
|--------|------|------|
| X 个 | Y 个 | file1.cs, file2.cs |

编译错误清单：
1. `文件:行号` — 错误信息 → 修复方式
2. ...
```

### 最终输出

```markdown
## 编译-修改循环完成

| 轮次 | 错误数 | 修复 |
|------|--------|------|
| Round 1 | 3 | 3 |
| Round 2 | 0 | 0 |

总计：X 个错误，Y 轮修复，循环终止原因：编译通过
```

### 注意事项

- 编译验证通过后，逻辑审查期间如引入编译错误，优先修复
- 如果编译错误涉及跨文件引用，检查所有引用方
- 保留每轮的编译输出，便于定位问题
- **最大轮次：10 轮**。达到 10 轮仍未通过，停止循环，在报告中标注「已达到最大编译轮次，以下为遗留编译错误」。

## 禁止事项

| ❌ 禁止 | 原因 |
|--------|------|
| 未经用户授权直接修改代码 | 修复需用户确认 |
| 强制要求重构 | 权衡成本收益 |
| 引入新问题 | 建议需验证可行性 |
| 自行审查 | 审查环节必须派 subagent |
